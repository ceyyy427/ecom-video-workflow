# 07 · Review Analysis Agent

**评论分析智能体** · 从评论原文里找出**买家真正在意什么**，然后告诉 Listing 该改哪一句。

> **v0.4 Skill 化**：新增 [`SKILL.md`](./SKILL.md)（分工边界：**分类交给模型、计数交给脚本**）+
> [`scripts/review_stats.py`](./scripts/review_stats.py)（**确定性聚合**：
> 好评/中评/差评分布、八类归因计数与占比、**归因合计 ≠ 差评数自动报错**、
> 可修复率、卖点频次 × 情感权重排行；列名自动识别中/英/葡，数字兼容巴西格式）。
> 统计实测：128 条 / 差评 13 / 可修复 11 = 84.6%，与案例文档完全一致。

---

## 一、它解决什么问题

SOP 1.6 里有一句话，是本模块的全部立论基础：

> **评论分析要单独列出来，因为评论是最接近真实买家需求的地方。**

但运营看评论的常见方式很低效：翻一遍、记住几条、"感觉质量还行"。真正的问题在于**评论里的信息没有被结构化**——所以它没法回馈到 Listing 上。

| 痛点 | 表现 | 本模块怎么解 |
|---|---|---|
| **评论看了但用不上** | 知道有差评，但不知道该改详情页哪一句 | 强制输出「差评 → 详情页动作」的映射 |
| **分不清问题归谁** | 把物流慢、买家误解、产品缺陷混成一类 | 按 SOP 八类归因，**误解型单独拎出来** |
| **卖点凭感觉排序** | "我觉得快充是卖点" | 用提及频次 × 情感强度定量排序 |
| **参数红线看不见** | 反复被投诉参数不符，但没提炼成禁用词 | 输出 `forbidden_words` 候选 |

**产出物**：好评/差评分类与归因 → 误解型差评清单 → 卖点频次排序 → 参数红线 → 详情页修补建议。

## 四、八类差评归因（SOP 1.6）

SOP 明确列出了差评要看什么。把它转成可判定的归因分类：

| # | 归因类型 | 判定特征 | 责任方 | 修复手段 |
|---|---|---|---|---|
| 1 | **误解型** ⭐ | 产品没问题，是描述没说清 | **我方（详情页）** | **改详情页 / 注意事项段** |
| 2 | 产品质量问题 | 实际存在缺陷、做工问题 | 供应商 / 我方 | 换供应商 / 改产品 |
| 3 | 参数不符合预期 | 描述与实物有差距 | 我方 | 修正参数描述 / 参数三处一致 |
| 4 | 配件缺失 | 买家以为含某配件 | **我方（包装清单图）** | 补包装清单图 + 明确"不含什么" |
| 5 | 发货慢 | 物流时效问题 | 物流 / 我方 | 改发货承诺 / 换物流 |
| 6 | 使用困难 | 上手门槛高、说明书不清 | **我方（说明书/详情页）** | 补使用指引图 |
| 7 | 售后差 | 客服响应慢、解决方案不满意 | 我方 | 改客服话术 / 流程 |
| 8 | 破损 / 故障 / 退货 | 运输破损或功能故障 | 物流 / 供应商 | 改包装 / 换供应商 |

### 为什么「误解型」要单独拎出来

| | 误解型 | 其他七类 |
|---|---|---|
| 能否靠文案修好 | ✅ **能** | ❌ 不能（要改产品/物流/流程） |
| 修复成本 | **接近零**（改详情页一句话） | 高（换供应商、换物流、改产品） |
| 修复周期 | **改完立即生效** | 数周到数月 |
| 投资回报率 | **最高** | 递减 |

> **误解题差评是唯一一类"改一句话就能消除"的差评。** 它不占多数，但它是**性价比最高的修复项**——所以本模块把它作为核心输出，而不是混在差评总数里。

**关键区分**：一条差评到底是"产品质量问题"还是"误解"？

- `A bateria dura pouco`（电池不耐用）→ 需要追问：是产品真不耐用，还是买家以为 20000mAh 能给笔记本充电？**后者是误解。**
- `Não veio o cabo`（没来数据线）→ 如果产品本来就不含数据线，**这是误解**，不是缺件。

> **判断标准**：如果 100% 按描述发货、产品也无缺陷，买家仍然不满，那就是**描述的问题**，归为误解型。

## 五、输出给 Listing 的三类回流

这是本模块存在的理由。**分析不是为了出报告，是为了改 Listing。**

| 回流类型 | 内容 | 消费者 | 具体动作 |
|---|---|---|---|
| **A. 详情页修补建议** | 差评问题 → 建议写进详情页第 6 段（注意事项）的条目 | **03 Listing** | 补写注意事项段 |
| **B. 参数红线** | 被反复投诉"不符预期"的参数 → 禁用词候选 | **03 / 04 / 05** | 加入 `forbidden_words`，全链路硬拦截 |
| **C. 卖点排序** | 按提及频次 × 情感强度排序的卖点 | **03 / 04** | 决定主图核心文案与标题关键词 |

### 回流示例

```text
输入：评论中提到 "esperava que viesse o cabo longo" 出现 7 次
        ↓
归因：误解型（产品没问题，是买家以为含长数据线）
        ↓
回流 A：详情页注意事项段增加 "O cabo incluso (USB-C) tem 30 cm"
回流 B：把 "cabo longo" 列入 forbidden_words（避免标题/图内暗示含长线）
回流 C：包装清单图必须明确标注线材长度
```

## 八、合规：什么是"处理差评"的正当边界

SOP 3.7 里的差评处理流程，包含若干本仓库**不实现**的动作。这里的边界必须讲清楚：

| SOP 原始表述 | 性质 | 本模块处理 |
|---|---|---|
| 给差评点举报，有机会消除差评 | 平台规则允许的申诉，但**组织性举报**属滥用 | ⚠️ 保留"单条明显违规评论可正常申诉"，**移除"组织举报"** |
| 联系客户删差评，说删了会很快退款并给补偿 | **以利益诱导删评** | ❌ 移除 |
| 产品有虚标的话可以说是说明书打包错了，我们产品有几个规格 | **以不实理由解释参数不符** | ❌ 移除 |
| 先回复差评，撇清责任表明态度 | 视情况，撇责式回复损害信任 | ⚠️ 改为"如实说明 + 给出解决方案" |
| **反向优化详情页、客服话术或产品** | ✅ **完全正当** | ✅ **保留并强化为本模块核心** |

> **归因分析的正当用途是改进自己的产品和描述，不是消除不利信息。**
> 这也是本模块把"误解型差评 → 详情页修补"作为核心输出的原因——**它把"想消除差评"这个诉求，转换成了一件真正该做的事。**

## 九、边界与限制

| 项 | 说明 |
|---|---|
| ✅ 负责 | 评论分类归因、误解型识别、卖点排序、参数红线、详情页修补建议、客服话术建议 |
| ❌ 不负责 | 实际修改 Listing（交给 03/04）、后台操作、联系买家 |
| ⚠️ 样本量 | 评论 < 20 条时，频次排序不具统计意义——Agent 会标注"仅供参考" |
| ⚠️ 无法验证真伪 | 无法判断评论是真实买家还是刷评，**归因基于文本内容，不基于真实性判断** |
| ⚠️ 语言问题 | 葡语/西语评论的口语化与错别字较多，可能影响分类准确度 |
| ⚠️ 评论被删风险 | 平台会删除部分评论，导致样本不完整 |
